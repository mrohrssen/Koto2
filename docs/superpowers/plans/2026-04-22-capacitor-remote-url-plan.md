# Capacitor Remote-URL Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Switch the iOS Capacitor WebView from the bundled `dist/` folder to loading directly from `https://jrpg-production.up.railway.app`, so frontend changes pushed to Railway appear on the device without a Xcode rebuild.

**Architecture:** Add a `server` block to `capacitor.config.ts`. Run `npm run build && npx cap sync ios` once to regenerate the iOS project with the new config. Rebuild and install on-device via Xcode one final time. From then on, any JS/CSS push to Railway `master` is visible on next app cold start.

**Tech Stack:** Capacitor 8.3, Vite 5 (build), TypeScript (config), Railway (hosting), Xcode 15+ (iOS build).

**Spec:** `docs/superpowers/specs/2026-04-22-capacitor-remote-url-design.md`

---

## File Structure

- **Modify:** `capacitor.config.ts` — add a `server` block with the Railway URL.
- **No other source files change.** The iOS project at `ios/` and build output at `dist/` are both gitignored; they get regenerated by `cap sync` and `vite build` respectively.

## Why this plan looks different from a typical TDD plan

This is a configuration change plus a manual on-device verification sequence. There is no new code to unit-test, so the normal "write failing test → make it pass" TDD loop doesn't apply. The verification step list functions as the test: each on-device check is a specific, falsifiable claim about the new build's behavior.

## Task 1: Add `server` block to `capacitor.config.ts`

**Files:**
- Modify: `capacitor.config.ts`

- [ ] **Step 1: Read current config**

Run: `cat capacitor.config.ts`

Confirm the current file has `webDir: 'dist'` and no `server` block.

- [ ] **Step 2: Edit `capacitor.config.ts` to add the `server` block**

Insert the `server` block between `webDir` and the `ios` block:

```ts
import type { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.koto.app',
  appName: 'Koto',
  webDir: 'dist',
  server: {
    url: 'https://jrpg-production.up.railway.app',
    cleartext: false,
  },
  ios: {
    contentInset: 'never',
    allowsLinkPreview: false,
    scrollEnabled: false,
  },
  android: {
    allowMixedContent: false,
    captureInput: true,  // Proper Japanese IME handling
  },
  plugins: {
    SplashScreen: {
      launchShowDuration: 2000,
      backgroundColor: '#e8edf3',
      showSpinner: false,
      launchAutoHide: true,
    },
    StatusBar: {
      style: 'LIGHT',
      backgroundColor: '#e8edf3',
    },
    Keyboard: {
      resize: 'body',
      resizeOnFullScreen: true,
    },
  },
};

export default config;
```

- [ ] **Step 3: Quick syntax check**

Run: `npx cap config`

Expected: Capacitor CLI prints the resolved config JSON and does not throw. The printed output should contain a `server` block matching what you wrote. If it errors with a parse/syntax complaint, the TS file is malformed — re-read the diff and fix.

This is preferred over raw `tsc` because Capacitor parses its own config through a bundled compiler and will tolerate config files that standalone `tsc` rejects due to missing ambient types.

## Task 2: Regenerate web bundle and sync to iOS

**Files:** (all gitignored — no git changes from this task)
- Regenerate: `dist/` (via `vite build`)
- Regenerate: `ios/App/App/public/` (via `cap sync`)
- Regenerate: `ios/App/App/capacitor.config.json` (via `cap sync`)

- [ ] **Step 1: Build the web bundle**

Run: `npm run build`

Expected: `vite build` completes successfully. Last lines show built assets in `dist/assets/` with hashed filenames like `index-<hash>.js`. No errors.

If `scripts/tokenize-static.js` (first phase of the build script) fails, fix that before proceeding — it means dialogue data is in a broken state, unrelated to this change.

- [ ] **Step 2: Sync to iOS**

Run: `npx cap sync ios`

Expected output ends with something like:
```
✔ Copying web assets from dist to ios/App/App/public in ...s
✔ Creating capacitor.config.json in ios/App/App in ...ms
✔ Updating iOS plugins in ...ms
✔ Sync finished in ...s
```

If `cap sync` errors with "web assets not found" or similar, it means Step 1 didn't actually populate `dist/`. Re-run `npm run build` and check that `dist/index.html` exists.

- [ ] **Step 3: Verify the synced config contains the `server` block**

Run: `cat ios/App/App/capacitor.config.json | python3 -m json.tool`

Expected: the printed JSON contains a top-level `"server"` key with `"url": "https://jrpg-production.up.railway.app"` and `"cleartext": false`. If it does not, the `capacitor.config.ts` edit was not picked up — go back to Task 1.

## Task 4: Final Xcode rebuild and install on device

This is a manual step — `xcodebuild` from the CLI can compile, but installing on a physical iPhone requires the Xcode GUI to pick the development team and signing certificate. The user performs this step.

- [ ] **Step 1: Open the iOS workspace**

Run: `open ios/App/App.xcworkspace`

Expected: Xcode opens with the "App" project.

- [ ] **Step 2: Select the physical device as the run target**

In Xcode's top bar, click the device selector (between the scheme name and the play button). Pick the connected iPhone — not a simulator.

- [ ] **Step 3: Clean the build folder**

Xcode menu: **Product → Clean Build Folder** (⇧⌘K).

This guarantees the new `capacitor.config.json` is picked up — Xcode sometimes caches resource bundles and incremental builds don't always re-copy them.

- [ ] **Step 4: Build and run**

Click the play button (▶) or ⌘R.

Expected: the app builds, installs on the iPhone, and launches automatically. First launch after the origin change will show the login screen (see Task 5 for the auth reset).

If the build fails with a code-signing error, fix the signing configuration in the **Signing & Capabilities** tab of the App target — unrelated to this change.

## Task 5: On-device verification — origin, auth, gameplay

These steps confirm the WebView is actually loading from Railway and that the app functions end-to-end at the new origin.

- [ ] **Step 1: Attach Safari Web Inspector**

On the Mac: Safari → Settings → Advanced → enable "Show Develop menu in menu bar". Then Safari → Develop → `<iPhone name>` → `Koto`. (If the app doesn't appear, on the iPhone: Settings → Safari → Advanced → Web Inspector ON.)

Expected: a Web Inspector window opens attached to the app's WebView.

- [ ] **Step 2: Confirm origin in the console**

In the inspector console, run: `location.origin`

Expected: `"https://jrpg-production.up.railway.app"`.

If it still shows `"capacitor://localhost"`, the `cap sync` in Task 2 did not update the iOS project, or Xcode is running a cached build. Re-run Task 2, then Task 4 Step 3 (clean) and Step 4 (rebuild).

- [ ] **Step 3: Log in with a test account**

In the app, complete the login flow with a known test user.

Expected: login succeeds. In the Web Inspector, run `localStorage.getItem('authToken')` — the token should be a non-empty string.

Note: The AI provider settings (`jrpg_aiApiKey`, `jrpg_aiProvider`, etc.) are also wiped by the origin change. If the user had a personal AI key configured, they'll need to re-enter it in the settings page. The server-side AI key is a fallback, so the smoke test in Step 4 should still work even before the personal key is re-entered.

- [ ] **Step 4: Gameplay smoke test**

From the starting screen, play through until you reach combat: area select → enter area → encounter → engage in one round of combat → either win or retreat.

Expected:
- Sprites render (both creatures visible, no broken-image placeholders).
- Combat card flip + swipe interaction works.
- TTS plays when a Japanese word is spoken.
- Haptics fire on card swipe.
- Web Inspector console shows no red-level errors unrelated to this change.

If any of these fail, first confirm the same user can play the exact same area by logging into the web app (`jrpg-production.up.railway.app`) directly in desktop Safari. If the web app works but the iOS build does not, that's a Capacitor-specific regression — gather the console error and pause the rollout.

## Task 6: Prove live-updates work

The whole point of this change. Demonstrate an unbroken loop: edit JS → push to Railway → see change on phone without touching Xcode.

- [ ] **Step 1: Pick a trivial visible string to change**

A safe choice is the app title shown in `public/game.html` or a visible menu label. Run: `grep -n "Koto" public/game.html | head -5` to find a candidate. Pick one that is visible at app cold start (e.g., in the landing/login screen markup), not behind a logged-in-only screen.

Good candidate: document title, loading text, or a heading. Record the exact string and its file:line.

- [ ] **Step 2: Make the edit**

Change the string to something recognizably different (e.g., append " — live update test"). Save the file.

- [ ] **Step 3: Commit and push to master**

Run:
```bash
git add <the edited file>
git commit -m "chore(test): live-update verification string"
git push origin master
```

Expected: push succeeds.

- [ ] **Step 4: Wait for Railway deploy**

Run: `curl -s -o /dev/null -w "%{http_code}\n" https://jrpg-production.up.railway.app/` every ~10s until it returns `200`. Railway deploys typically take 1-3 minutes.

Alternative: watch the Railway dashboard deploy log.

- [ ] **Step 5: Force-close the app on the iPhone**

On the phone: swipe up from the bottom, find Koto in the app switcher, swipe the card up to kill it. This is important — simply backgrounding the app is not enough because iOS may keep the WebView warm and serve a cached `index.html`.

- [ ] **Step 6: Relaunch and verify**

Open the app from the home screen. Check the screen where you made the string change.

Expected: the new string is visible. If it is, **the remote-URL loop is working** — this is the success criterion of the whole plan.

If the old string persists: check in Web Inspector that `document.title` (or whatever you changed) actually reflects the edit. If it does but the screen doesn't, there's a UI-layer render caching issue. If it does not, the WebView is serving a cached response — try turning airplane mode on and off once to kick the WebView cache, or revoke the app and reinstall.

- [ ] **Step 7: Revert the test string**

Run:
```bash
git revert HEAD
git push origin master
```

Or manually edit back and push. The repo should not carry the "live update test" string.

## Task 7: Spot-check failure mode

Confirms what users see if Railway is unreachable. The spec documented this as accepted — this step just verifies what was predicted.

- [ ] **Step 1: Enable airplane mode on the iPhone**

Swipe down from top-right → tap airplane icon. Confirm the status bar shows the airplane symbol.

- [ ] **Step 2: Force-close the app**

Same procedure as Task 6 Step 5.

- [ ] **Step 3: Launch the app**

Tap the Koto icon.

Expected: within a few seconds, the WebView shows its "cannot load page" state. Exact visual depends on iOS version — usually a white screen with a small error line like "Safari cannot connect to the server". This is acceptable per the spec's accepted tradeoff.

- [ ] **Step 4: Turn airplane mode off**

Tap the airplane icon again. Wait for cell/wifi to reconnect.

- [ ] **Step 5: Force-close and relaunch**

Expected: app loads normally. Login state is preserved (because `authToken` is still in localStorage for the Railway origin).

## Rollback (only if needed)

If App Store review later rejects the remote-URL build, or if a critical issue surfaces:

1. Revert the commit from Task 3: `git revert <commit-hash> && git push origin master`.
2. Run: `npm run build && npx cap sync ios`.
3. Rebuild in Xcode, install on device.

All users flip back to the `capacitor://localhost` origin and must log in once more + re-enter AI provider settings. No server-side data is affected.

All checkboxes in Tasks 1-7 are checked. Task 6 Step 6 (the "new string is visible without an Xcode rebuild" moment) is the single most important success criterion — if that works, the plan has achieved its goal.
