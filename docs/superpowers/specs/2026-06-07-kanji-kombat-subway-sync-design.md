# Kanji Kombat Subway Sync Design

**Date:** 2026-06-07
**Status:** Approved behavior, pending implementation plan
**Feature:** In-session review continuity during dropped or slow connections

## Summary

Kanji Kombat should feel good on a subway, on hotel Wi-Fi, or anywhere else the network drops for a few seconds. The player should not lose the rhythm of a language review session because the server response is late or missing.

The product rule is:

> The learner's flow is the truth the UI protects. The server is the durable sync target.

Kanji Kombat should consume reviewed prompts locally, keep moving while it has buffered prompts, and sync those reviews to the server in the background. Server state still owns durable SRS, rewards, daily completion, leaderboards, and final combat truth. It should not casually rewind the player to a prompt they already answered during the same active session.

## Goals

- Let Kanji Kombat continue through short network drops without replaying already answered cards.
- Keep review prompts locally consumed during the active session once the player answers them.
- Use an in-memory sync queue for intro choices, quiz answers, and completion choices.
- Continue combat quiz turns client-side through the existing deterministic prediction path.
- Reconcile quietly with the server when connectivity returns.
- Show soft connection copy only when the player needs to know why the game has paused.

## Non-Goals

- No IndexedDB or persistent offline queue in this phase.
- No guarantee that unsynced reviews survive a reload, crash, or browser close.
- No client authority over durable SRS state, rewards, leaderboard records, or daily-complete markers.
- No replay of arbitrary future server state that the client did not already receive through the prompt buffer.
- No changes to Speed Review behavior.

## Existing Behavior Reference

Hub Speed Review already protects flow over strict save confirmation. It advances the visible card immediately, keeps a pending undo review, and uses in-flight promises for background sync. Rejected review writes are logged without rewinding the card stream.

The repo still contains a disabled/legacy `speedReviewRoom` room type used by tests and older plans, but it is not generated by the current Koto2 room system and is not part of the current player-facing comparison for this design.

Kanji Kombat should follow the active hub Speed Review product instinct for review flow, while keeping combat and rewards reconciled through its existing predictive combat and server-validation machinery.

## Core UX Rules

Once the client visibly consumes a Kanji Kombat prompt, it should not intentionally show that same prompt again during the same active session just because the server response was slow, missing, or temporarily failed.

The UI can advance through buffered prompts while sync is pending. The player should see normal Kanji Kombat action, not a save spinner after every card.

If connectivity drops and the client still has buffered prompts, the session continues.

If connectivity drops and the prompt buffer is empty, the session pauses on a stable screen with soft copy:

`Connection is spotty. Your reviews will sync when you reconnect.`

The player should only be asked to retry a choice when the client cannot continue and cannot reconcile to a usable state.

Avoid ordinary dropped-response copy like:

- `Kanji Kombat choice did not save. Please try again.`
- `Invalid choice.`
- `Synced with server.`

## In-Memory Sync Queue

Kanji Kombat gets a session-local `reviewSyncQueue`. It is held in memory only and reset when the Kanji Kombat UI/module is initialized or the page reloads.

Each queue item contains:

```javascript
{
  actionId: 'run_...',
  kind: 'intro' | 'quiz' | 'completionChoice',
  promptId: 'kkp_...',
  sequence: 12,
  cardId: 'hiragana:か',
  choice: 'known',
  answerId: 'choice_ka',
  keepGoing: true,
  predictedHash: '...',
  createdAt: 1780000000000,
  attempts: 0,
  status: 'pending' | 'syncing' | 'accepted' | 'corrected' | 'failed'
}
```

Fields that do not apply to a prompt kind are omitted. Quiz items include the existing optimistic combat envelope or enough data to rebuild/send it using the current predictive combat path.

Queue behavior:

1. Add an item when the player answers a prompt.
2. Consume the prompt locally immediately.
3. Start or continue a background drain loop.
4. Retry pending items with modest backoff when requests fail.
5. Remove items when the server accepts or replays the same `actionId`.
6. Apply corrections to combat/server-owned state without replaying consumed prompts when the local session can still continue.

The queue is ordered. A later item should not be committed before an earlier item if the server contract requires prompt sequence order. If later independent responses arrive first, they wait until earlier queue items are resolved or corrected.

### Queue Size And Backpressure

The in-memory sync queue is bounded.

Use these initial constants:

```javascript
const REVIEW_SYNC_QUEUE_SOFT_LIMIT = 40;
const REVIEW_SYNC_QUEUE_HARD_LIMIT = 60;
const REVIEW_SYNC_QUEUE_RESUME_LIMIT = 30;
```

Behavior:

- At `0-39` pending items, play continues normally.
- At `40-59` pending items, play can continue from already buffered prompts, but the UI should prioritize draining and should not request optional extra runway beyond the normal prompt-buffer target.
- At `60` pending items, Kanji Kombat pauses before consuming another prompt and shows `Connection is spotty. Your reviews will sync when you reconnect.`
- Play resumes automatically once the queue drains to `30` or fewer pending items and a usable prompt/action is available.

Sixty queued reviews is intentionally generous for an in-memory subway session. It gives the player enough runway for several minutes of review while preventing unbounded local divergence if the server is unreachable for a long time.

### Sync Drain Loop

The server does not initiate sync. The client owns the drain loop and keeps trying to commit queued reviews while allowing play to continue within the queue and prompt-buffer limits.

Drain triggers:

- immediately after enqueueing a review;
- immediately after an accepted/replayed item is removed;
- after a prompt-buffer refill succeeds;
- when the browser fires `online`;
- when the page becomes visible again;
- after the retry timer for the current head item fires.

Only one queue item is sent at a time while prompt sequence order matters. If the head item succeeds, the client immediately attempts the next item. If the head item fails because the network is slow or unavailable, it stays at the head of the queue and retries with backoff:

```javascript
const REVIEW_SYNC_RETRY_DELAYS_MS = [0, 500, 1000, 2000, 4000, 8000, 15000];
```

After the final delay, retry every `15000` ms while the page is active. `online` and `visibilitychange` events can trigger an immediate drain attempt instead of waiting for the next timer.

While the queue is retrying, the client may keep advancing through already buffered prompts until either:

- the prompt buffer is exhausted; or
- `REVIEW_SYNC_QUEUE_HARD_LIMIT` is reached.

In other words, the client can get ahead of the server, but only up to the bounded local runway. Sync is aggressive on success, patient on failure, and never an unbounded tight loop.

## Prompt Buffer

Kanji Kombat should keep a larger server-prepared prompt buffer than the current screen needs. The buffer is the player's runway through spotty connectivity.

Use these initial constants:

```javascript
const PROMPT_BUFFER_TARGET = 30;
const PROMPT_BUFFER_REFILL_THRESHOLD = 10;
```

The current implementation uses a much smaller runway (`5` target, `3` refill threshold). Subway sync should raise that to a 30-prompt target with refills beginning when 10 prompts remain.

The runway is a mixed server-prepared prompt buffer, not a due-only queue. It can contain:

- due-card quiz prompts;
- new-card intro prompts when the normal new-card cadence fires;
- no-due new-card intro/practice prompts within the existing no-due discovery-chain rules;
- a completion prompt when no eligible work remains.

The buffer must preserve the existing Kanji Kombat selection rules. Raising the target to 30 must not mean "prefill 30 new cards." The server still chooses the mix using due-card state, `reviewsSinceIntro`, `nextIntroAfter`, daily new-card cap, no-due discovery-chain limit, endless-mode rules, and completion state. New-card intros in the buffer are preview runway only; durable daily new-card counts are committed when the intro choice syncs, not when the prompt is buffered.

The client should request refills opportunistically:

- after consuming a prompt if the buffer is below the threshold;
- after a successful sync batch;
- when the browser reports connectivity restored;
- after returning to an ally action cursor.

If the server cannot refill but the client still has prompts, the player keeps playing. If the buffer is exhausted, the player sees the spotty-connection pause.

The client must not invent new cards outside the server-prepared buffer. It can continue only through prompts it already received or through deterministic combat state it can predict from existing state.

## Prompt Consumption Rules

### Intro Choices

`I already know it` and `I didn't know it yet` consume the intro prompt immediately.

The client:

1. Adds an `intro` queue item with `actionId`, prompt metadata, card id, and choice.
2. Removes the intro prompt from the local prompt buffer.
3. Advances to the next local prompt if available.
4. Drains the queue in the background.

If the server later rejects the intro because it was already accepted, stale, or duplicated, the client reconciles to accepted/replayed state and does not replay the intro during this active session.

### Quiz Answers

Quiz answers drive combat and should be handled client-side first.

The client:

1. Marks the quiz prompt consumed locally.
2. Builds the existing optimistic Kanji Kombat combat envelope.
3. Plays the predicted combat transcript immediately.
4. Adds a `quiz` queue item for server verification/commit.
5. Keeps moving when the next prompt/action is locally available.

The server later accepts, replays, or corrects the action.

Accepted or replayed actions remove the queue item. Corrected actions patch server-owned combat state, including HP, enemies, streak counters, wave state, and prompt buffer. Corrections should not replay the already answered quiz prompt unless the client cannot continue from any coherent local or server state.

### Completion Choices

Completion choices consume the completion prompt locally, but durable daily completion and final rewards still wait for server acceptance.

If the player chooses to keep going, local endless mode can continue while the completion choice syncs. If the player chooses to stop and the network is unavailable, show a stable pending-completion state rather than claiming the daily complete report is durable.

## Reconciliation Rules

Server state is still authoritative for durable data:

- FSRS scheduling and card reps.
- Daily new-card count and daily-complete state.
- Combat HP, enemies, turn seeds, and wave state after correction.
- Streak rewards and run-scoped reward state.
- Leaderboards and reports.

Client state is authoritative for in-session consumed prompt UX:

- A consumed prompt should stay consumed while the session is active.
- A server response that is merely behind the client should not force a prompt replay.
- A fetched server state that lacks locally consumed prompts is treated as behind until queued items are accepted, corrected, or impossible to reconcile.

When sync resumes:

1. Drain queued actions in order.
2. Accept duplicate/replayed `actionId` responses as success.
3. Apply accepted server state while preserving local consumed prompt markers for pending later items.
4. Apply corrections to server-owned state.
5. Drop local consumed markers only when the session ends, reloads, or the server correction makes continuation impossible.

If the server returns a hard correction that changes the visible action cursor or combat state, resync battle sprites to the corrected state. If the current prompt remains locally coherent, do not show the old answered card again.

## Error Handling

Short network failure while prompts remain:

- Continue silently.
- Keep retrying in the background.
- Optionally show a small passive connection indicator if a general connection banner already exists.

Buffer exhausted while unsynced:

- Pause interaction.
- Show `Connection is spotty. Your reviews will sync when you reconnect.`
- Retry sync/refill until a prompt or final state is available.

Server correction:

- Patch combat state and sprites.
- Continue from the corrected next prompt if one exists.
- Avoid replaying consumed prompts unless there is no coherent alternative.

Reload with unsynced in-memory queue:

- Queue is lost.
- The server state wins.
- The player may see those cards again in a later session because they were not durably reviewed.

## Architecture

Keep the implementation local to Kanji Kombat and the combat loop instead of creating a global offline system.

Suggested units:

- `kanji-kombat-sync-queue.js`: owns in-memory queue state, enqueue, drain, retry, and status helpers.
- `kanji-kombat.js`: consumes intro/completion prompts locally and delegates queueing.
- `combat-loop.js`: lets Kanji Kombat quiz answers continue using predictive combat while verification is queued/drained.
- Existing API functions remain the server commit mechanism.

The queue should expose a small interface:

```javascript
enqueue(item)
drain()
hasPending()
pendingCount()
markAccepted(actionId, response)
markCorrected(actionId, response)
reset()
```

The drain loop should avoid concurrent commits for sequence-sensitive items. It should be safe to call `drain()` repeatedly after every prompt, refill, online event, or state sync.

## Testing

Unit tests:

- Intro choice consumes the prompt locally and enqueues a sync item.
- Null intro response does not restore the consumed prompt while another local prompt exists.
- Intro queue accepts duplicate/replayed `actionId` responses.
- Queue backpressure allows play below 40 pending items, warns/prioritizes draining from 40-59, pauses at 60, and resumes at 30.
- Sync drain loop sends one head item at a time, drains immediately on success, retries failed head items with `[0, 500, 1000, 2000, 4000, 8000, 15000]`, and resumes on `online` or visibility restore.
- Quiz answer builds an optimistic combat envelope, consumes the prompt, and enqueues verification.
- Quiz answer continues through a delayed/null server response when a next buffered prompt exists.
- Corrected quiz response patches combat state and resyncs sprites without replaying the answered card when continuation is coherent.
- Prompt buffer requests refill at 10 remaining prompts and targets 30 prompts.
- Prompt buffer target includes due quizzes, cadence-eligible new-card intros, no-due intro/practice prompts, and completion prompts without bypassing daily new-card limits.
- Buffer exhaustion shows the spotty-connection pause.
- Reload/reset drops the in-memory queue and accepts server state.

Integration tests:

- Simulate several Kanji Kombat answers with delayed server responses and verify the UI advances.
- Simulate server catch-up after delayed responses and verify queued actions are removed.
- Simulate a stale server state fetch while local queue has pending consumed prompts and verify no replay.
- Simulate a hard correction and verify state/sprites are patched.

Manual playtest:

- Throttle or interrupt network during Kanji Kombat.
- Answer several cards while requests are delayed.
- Confirm cards do not jump backward.
- Restore network and confirm sync drains quietly.
- Exhaust the prompt buffer while offline and confirm the soft pause appears.

## Open Questions

No open product questions remain for the in-memory version. A future offline-first design can revisit persistent queues, IndexedDB, and reload survival.
